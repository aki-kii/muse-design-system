失敗からのやり直し（Error Recovery）

操作が失敗しても入力を残し、理由と「もう一度」をその場に出す

デモ

失敗しても入力は消えず、ボタンの近くに理由と次の一手が出て、同じボタンでやり直せます。

よくある型である理由: 送信・保存・作成などの操作は、どの製品でも通信や処理の失敗で止まることがあります。そのときに入力を失わず、何が起きたかと次の一手をその場で示す流れは、エラー処理の基本の型です（GOV.UK の Recover from validation errors、NN/g の Error-Message Guidelines、Primer の Degraded experiences）。

使っているところ: 学習ノート（採点・作成・質問の送信が失敗したとき、入力を残して「もう一度」を出す）、入力バーの音声入力のエラー。

概要#

本人が始めた操作が失敗したときに、入力をそのまま残し、失敗したことと理由を操作のすぐ近くに文で出し、同じ操作をもう一度できるようにする流れです。

組み合わせ#

  • 操作: ボタン（送信中は無効にして文を変える）
  • 入力: 入力欄・入力バー（失敗しても中身を消さない）
  • 知らせ: 操作の近くに --danger の文（入力欄のエラーと同じ出し方）

流れ#

段階見た目次へ
実行中ボタンを押せなくし、文を「送信中…」のように変える成功か失敗
成功結果を出し、入力を空に戻す。必要ならトースト
失敗入力を残したまま、ボタンを押せる状態に戻す。ボタンの近くに「送れませんでした。もう一度試してください」のように、何が起きたかと次の一手を1文で出すもう一度押したら実行中へ
  • 失敗の文は操作のすぐ近くに出す。画面の上の帯やトーストだけで知らせない（消えると読めない）。
  • 入力の中身が原因の失敗（形式の誤り）は、その欄のヒントの位置に出し、欄にフォーカスを戻す。
  • ボタンの文を「もう一度送る」に変えてよい。
  • 何度も失敗するときも、同じ流れのまま。勝手に繰り返し送らない。

使うとき#

  • 本人が押して始めた送信・保存・作成・採点などの操作が失敗したとき

使わないとき#

  • 画面を開いたときの読み込みの失敗 → 読み込み・空・失敗の状態
  • 取り消せない操作の前の確認 → 確認をはさむ操作

アクセシビリティ#

  • 失敗の文は role="alert" で伝える（本人の操作の結果なので割り込んでよい）。
  • 欄の誤りは aria-invalid="true" と aria-describedby で欄に結び付ける。
  • 失敗は赤い色だけでなく文で伝える。
