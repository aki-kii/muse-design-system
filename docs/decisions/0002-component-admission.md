# 0002: コンポーネントには汎用の部品だけを置き、アプリ固有の複合体はパターンに置く

- 状態: 決定
- 日付: 2026-11-17

## 背景

v0.4.0（学習ノート）と v0.5.0（スライドエディタ）で、アプリを Muse DS で作り直すときに足りなかった部品を、そのままコンポーネントに足した。その結果、`docs/components/` には、ボタンやカードのような内容に依存しない部品と、「デッキカード」「単語カード」「スレッドカード」のように特定のアプリの言葉を持つ複合体が混ざった（汎用 9件に対して、アプリ由来 30件）。

この状態では、新しいアプリを作る人が「どれが使ってよい部品か」を一覧から判断できない。また、アプリ由来の部品は、そのアプリの事情（モックの値、アプリ固有の状態）をそのまま持っていて、別のアプリに持ち出すと意味が合わない。

実在のデザインシステムは、この問題を収載の基準と層の分け方で扱っている。

- [GOV.UK Design System](https://design-system.service.gov.uk/community/contribution-criteria/) は、部品やパターンを載せる前に「役に立つ（複数のサービスで使われている証拠がある）」「他と違う」「使えることが確かめられている」などの基準を満たすかを確かめ、満たすまでは「提案」の段階に置く。
- [Carbon Design System](https://carbondesignsystem.com/contributing/overview/) は、汎用の部品（Core）と、製品やチームごとの部品（拡張・コミュニティ）を分け、Core には多くの製品で使えるものだけを入れる。

## 決定

1. **`docs/components/` には、中身に依存しない汎用の部品だけを置く。** 部品の名前・状態・文に、特定のアプリの言葉（デッキ・章・スレッド・XP など）が要るものは置かない。アプリでの使い方は「例:」や「適用例」として書く。
2. **アプリ固有の複合体は `docs/patterns/<アプリ>/` に置く。** 部品の文書と同じテンプレートに「組み合わせ」の節を足し、どの汎用部品の組み合わせかを書く。
3. **2つ目のアプリで使われたら、部品への昇格を検討する。** 同じ形が2つのアプリで要ると分かった時点で、アプリの言葉を外して書けるかを確かめる。
4. **汎用にできるものだけを昇格する。** 外せたら汎用の名前で `docs/components/` に部品を新設し、元の複合体は「組み合わせ」にその部品を書く形にする。外せないものはパターンに残す。
5. **複合体の中に汎用の核がはっきりあるときは、1つ目のアプリの時点でも核だけを部品にしてよい。** 例: 単語カードの「表裏＋自己判定」をフラッシュカードとして、デッキカードの「サムネイル＋タイトル＋メタ情報」をメディアカードとして部品にした。核の形が既存の部品と重なるか、使い道が1つしか思いつかないときは部品にしない。
6. **移した文書の元の場所には、移行先への案内を残す。** リンクを切らないため、元のファイルを短い案内に置き換え、サイトでは移行先へ転送する。

## 結果

- v0.6.0 で、アプリ由来 30件のうち 23件をパターンに移し（学習ノート 12件、スライドエディタ 11件）、吹き出しに足していたスライドエディタ固有の拡張を「スレッドの会話」に移した。
- スライドエディタ由来のうち、もともと中身に依存しない 7件（シートモーダル、確認ダイアログ、作業中インジケータ、完了トグル・完了バッジ、スピードダイヤルFAB、長押しメニュー、入力バー）は、文書をアプリの言葉から外してコンポーネントに残した。
- 汎用の核として、フラッシュカード、進捗パス、メディアカード、状態付きリスト項目、アイコンボタン、選択肢ボタンの6件を新設した。
- 結果バナーの「消えずに残る知らせの帯」、章完了パネルの「終わりの画面」は、使うアプリが1つだけのため部品にせず、パターンに残した。2つ目のアプリで要ったときに 3・4 の手順で検討する。
- 困ること: 移した部品の URL（`components/<名前>.html`）は案内のページになり、本文は `patterns/<アプリ>/<名前>.html` に移る。ブックマークや外からのリンクは1回転送を挟む。
